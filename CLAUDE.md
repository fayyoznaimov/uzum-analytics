# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Uzum Analytics — a self-hosted seller analytics cabinet for the Uzum marketplace: sales, profit, cost price, warehouse, supplies, goals, Telegram notifications, and a "wallet" that forecasts when money lands in the Uzum withdrawal basket. npm-workspaces monorepo: `apps/api` (NestJS 11) + `apps/web` (Next.js 15 App Router, React 19), Postgres via Prisma, deployed with Docker Compose. Product, UI, docs, commits, and all user-facing strings are in **Russian** — keep new strings Russian.

## Commands

Run from the repo root unless noted. npm is required (`.npmrc` sets `legacy-peer-deps=true`).

If you change how Prisma models/enums are used in a way the stub doesn't cover, update the stub.

Tests: Vitest with no config file — any `*.spec.ts` under `apps/api` is picked up; they live in `__tests__/` folders beside the code they cover and almost all target the pure modules in `apps/api/src/common/`.

## Architecture

### API (`apps/api`)
- **No per-feature Nest modules.** A single `AppModule` (`src/app.module.ts`) registers every controller and provider flat. A feature = a folder `src/modules/<feature>/` with `<feature>.controller.ts` + `<feature>.service.ts`. When adding a feature, wire both arrays in `app.module.ts`.
- **Business logic is extracted into pure functions in `src/common/`** (`finance.ts`, `payout-basket.ts`, `payout-forecast.ts`, `order-state.ts`, `advertising.ts`, `inventory-report.ts`, `inventory-analytics.ts`, `sku-payout.ts`, `profit-days.ts`, `financial-statement.ts`, `fbo-supply-summary.ts`, `period.ts`, `pricing.ts`, `promo-pricing.ts`, `auto-pricing.ts`, `ai-price-review.ts`, `ad-agent.ts`, `ad-bot.ts`, `promo-plan.ts`). Services orchestrate Prisma + these functions; put testable logic here, not in services.
- Shared providers: `PrismaService`, `CryptoService`, `TelegramClient`.
- `main.ts`: global prefix `/api`, `helmet`, CORS restricted to `WEB_ORIGIN` (comma-separated), global `ValidationPipe` (`whitelist` + `forbidNonWhitelisted` + `transform`), env validation at boot (`DATABASE_URL`, `JWT_SECRET` ≥ 32 chars, `APP_ENCRYPTION_KEY`).
- **Auth**: JWT bearer, 12h expiry. `AuthGuard` is applied **per controller/route** with `@UseGuards(AuthGuard)`, not globally — new endpoints are public unless guarded. `ThrottlerGuard` is the one global guard. A single admin user is seeded from `ADMIN_EMAIL`/`ADMIN_PASSWORD`.
- **Integration credentials** (`UZUM`, `UZUM_INTERNAL`, `UZUM_CABINET_LOGIN`, `OPENAI`, `TELEGRAM`) are stored in the DB (`IntegrationCredential`), **encrypted at rest** with AES-256-GCM by `CryptoService` using `APP_ENCRYPTION_KEY` (base64, decodes to exactly 32 bytes). They are configured through the Settings UI at runtime, not via env.
- **Sync** (`SyncService`): `@Cron` jobs (schedules from env: `SYNC_CRON`, `ORDER_NOTIFY_CRON`, `SUPPLY_SYNC_CRON`, `SLOT_WATCH_CRON`, `AD_RATE_DIGEST_CRON`, …) pull from the Uzum Seller OpenAPI base `https://api-seller.uzum.uz/api/seller-openapi` (`/v1/shops`, `/v1/product/shop/:id`, `/v1/finance/orders`, `/v1/finance/expenses`). Manual run: `POST /api/sync/run`; poll `GET /api/sync/runs`. Sync is defensive: unrecognized payload shapes throw rather than wiping stored data; pagination has hard page caps.

### Core domain invariants — do not "improve" these casually
- **Money timeline**: `dateIssued` (actual handover to buyer) → 10 full calendar hold days → next day the amount becomes `basketEligibleAt` (enters the withdrawal basket) → then paid out on the shop's payout schedule. Returns reduce money automatically because the Finance API `order.payout` is already net of returns — basket/profit are computed from that net payout. A return *after* issue additionally writes a negative `OrderFinancialEvent` (`RETURN_REVERSAL`) into an audit-trail journal that nothing reads yet; write errors are logged and surfaced in the sync run message. Reference: `docs/UZUM_WALLET_BASKET.md`, `common/payout-basket.ts`, `common/payout-forecast.ts`.
- **Advertising spend for actuals is never modeled or averaged.** It is rebuilt solely from real Uzum expense-ledger rows — code `У000120` (per-order boost), `У000119` (top/campaign boost). Where the fact isn't published yet, the UI may show an estimate from the last *observed* per-product rate, always explicitly labeled as an estimate. `common/advertising.ts`.
- **All day/hour bucketing is `Asia/Tashkent`.** Use the `Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Tashkent' })` helpers in `common/period.ts` (API) / `web/lib/period.ts` (client). Don't add raw `new Date()` local-time date arithmetic. API list endpoints take `from` / `to` / `days` / `compare` query params resolved by `resolvePeriod`.
- Profit/margin figures are shown only when every input (payout, cost price, ad fact/coverage) is known; otherwise the code deliberately renders "не рассчитана" rather than a guess. Preserve that "known vs. estimated" distinction in any financial output, including Telegram messages.

### Web (`apps/web`)
- Next.js App Router. **Every `app/<route>/page.tsx` is a one-line re-export** of `components/<Name>Client.tsx`. All real UI lives in the `*Client.tsx` client components; keep it that way.
- `lib/api.ts`: `api()` fetch wrapper — JWT from `localStorage['ua_token']`, auto-`logout()` on 401, `NEXT_PUBLIC_API_URL` base (`/api` in prod). `money()` / `compact()` are ru-RU formatters. `syncAndWait()` triggers + polls a sync.
- `lib/period.ts`: `useAnalyticsPeriod()` hook — selected period persisted to `localStorage` and broadcast across components via a custom window event.
- Styling is **hand-written class-based CSS** in `app/globals.css` (+ `costs-ui.css`, `reviews-ui.css`), no Tailwind, no CSS modules. Charts: `recharts`. Icons: `lucide-react`.
- Web components are written in an intentionally dense, single-line style. Match the surrounding file rather than reformatting.
- `next.config.ts` rewrites `/api/:path*` → `API_INTERNAL_URL` (`http://api:4000` in Docker); `output: 'standalone'` unless `NEXT_OUTPUT_STANDALONE=false`.

### Мониторинг конкурентов и расширение (`extensions/uzum-monitor/`)
Публичный каталог uzum.uz с серверных IP закрыт антиботом, поэтому цены/остатки/счётчики заказов чужих карточек и позиции своих товаров в поиске снимает MV3-расширение в браузере владельца. Поток: экран «Конкуренты» выдаёт 6-значный код (`POST /api/competitors/pairing-code`, auth) → расширение меняет его на токен (`POST /api/competitor-watch/pair`) → далее `GET /api/competitor-watch/targets` и `POST /api/competitor-watch/ingest` с заголовком `x-watch-token` каждые ~3 часа. Логика алертов (демпинг ≥3%, пропал/появился товар → Telegram, дедуп сутки) — `common/competitor-watch.ts`; журнал — модели `CompetitorProduct`/`CompetitorSnapshot`/`SearchPositionSnapshot`. «Упущенная выручка» (экран Склад, `GET /api/warehouse/lost-revenue`) — оценка из `common/lost-revenue.ts`: скорость продаж в дни наличия × дни без остатка по `StockSnapshot`; всегда помечается как оценка.

## Workflow
- Development happens in the local clone on the owner's Windows PC or directly on the server in `~/uzum` (commit + push required; the auto-deploy pipeline only rebuilds when origin/main is AHEAD of the server HEAD, so after committing on the server run the build and `systemctl --user restart uzum-api.service uzum-web.service` manually, loading `.env` first: `set -a; . ./.env; set +a; npm run build`). **After each finished task** (not after every file save): run `npm test` and `npm run test:types:api` (plus `npm run test:web` if `apps/web` changed), then commit with a Russian message and `git push` to `main` without asking — the owner wants every finished change in Git right away. A push to `main` deploys to production within seconds, so never push failing checks or half-done work; say so if a check fails instead of pushing.
- Commands that need the production DB or Uzum/Telegram tokens (`apps/api/scripts/*.ts`, sync, price changes) only work on the server; `.env` and the DB are not in Git.

## Deploy notes
- **Production = ParisaUbuntu (172.0.30.4), rootless, no Docker**: `systemd --user` services `uzum-postgres`, `uzum-api` (port 4100), `uzum-web` (port 3200) in `~/uzum`. The unit files live in `~/.config/systemd/user/` (not in Git). Postgres is embedded (`~/pgsql`, port 55433); after an unclean reboot a stale `data/postmaster.pid` blocks `pg_ctl start` and takes `uzum-api` down with it (05.10.2026: 8 hours without sync and order notifications) — `uzum-postgres.service` now has an `ExecStartPre` that moves the pid file aside when no `postgres` process is running. If the API is "inactive (dead)", check `systemctl --user status uzum-postgres` first. Code flows through GitHub `main`: on push, a self-hosted GitHub Actions runner on the server (`.github/workflows/deploy.yml`, label `uzum-server`, unit `github-runner`) starts `uzum-deploy.service` → `scripts/auto-deploy.sh`; `uzum-deploy.timer` re-checks every 5 min as a fallback — ff-only pull → tests → type gate → build → `prisma db push` (no `--accept-data-loss`) → restart → health check, with automatic rollback and a Telegram message on failure. Log: `~/.local/state/uzum-deploy/deploy.log`. Don't edit the server's working copy directly — a dirty tree blocks deploys; commit and push instead.
- OpenClaw (AI turns for auto-pricing, ad agent, review replies — `common/openclaw.client.ts`): the API calls the `openclaw` binary from its service PATH with nvm directories stripped, so without `OPENCLAW_BIN` it picks `/usr/bin/openclaw` (2026.8.2, system). The owner's current OpenClaw lives in `~/.local/lib/node_modules/openclaw` (2026.9.8, also used by `openclaw-gateway.service` for the Telegram bots) and its migrations rewrite `~/.openclaw/openclaw.json` with keys the old binary rejects (`meta.migrations: Unrecognized key "utilityModelSeparation"`, 04–07.10.2026: every AI review failed). Fix in place since 07.10.2026: `OPENCLAW_BIN=/home/parisahome/.local/bin/openclaw` in `.env`. Never remove such keys from the config — the gateway writes them back; point the API at the same binary the gateway runs instead.
- Price changes: `PricingService.sendPrice` / `apps/api/scripts/send-price.ts` (dry-run by default, every attempt logged in `PriceChange`). Uzum rejects `sendPriceData` with `sku-price-001` while a SKU is in an Uzum promo; promo prices are only editable in the seller cabinet. The same error comes for SKUs in a **platform-funded promo «Скидка Uzum»** (cabinet shows the badge next to the price: "скидку компенсирует Uzum Market"): it is absent from `marketing/sales`, so `send-promo-price.ts --list` shows no positions, yet the base price is locked for the whole promo — nothing to do but wait (06.10.2026: every SKU of the shop was locked this way). The order payout rows carry the discounted amount; whether Uzum's compensation arrives as a separate finance operation is unverified — check before trusting per-SKU margin for those days. For Uzum promos (`specialOffer.mechanicType = UZUM_PROMO`) the OpenAPI `price` is the BASE price and OpenAPI does not report the promo or the crossed-out price; the buyer's current price and `specialOffer.inOffer` come from the cabinet `getProducts`. The owner deliberately keeps base prices above promo prices: the base price is the ceiling («не более») for the price inside a promo, so do not lower base prices to promo levels. The crossed-out price (`fullPrice`) does not affect the selling price; `scripts/set-full-prices.ts` / Actions «Зачёркнутые цены» sets it to base price +N% (`--markup 0` = equal to base), list-only unless `--apply`, and only works while SKUs are outside a promo. Promo prices go through the cabinet's internal API at `https://api.uzum.uz/api/seller/shop/{shopId}/marketing/sales/...` with the `UZUM_INTERNAL` token: `PromoPricingService` / `apps/api/scripts/send-promo-price.ts` (`--list` to read base price, promo price and the "не более" limit; dry-run by default; logged in `PriceChange` with `kind = PROMO`). Saving posts the whole product (all its SKUs in the sale), exactly like the cabinet does.
- Auto-pricing: rules in `common/auto-pricing.ts` (roles LOCOMOTIVE = лицевые incl. HAVANA 50×90 / MARGINAL, deficit/flow/revert/slow rules; SLOW lowers only with ≥ 60 days of stock AND margin ≥ 35% at the current price — at −5% price you need +17% units at 25% margin, textile elasticity is 1–2.5 — and never for products in `AUTO_PRICING_NO_LOWER_PRODUCTS` (saunas 2263224), promo "не более" limit → recommendation "поднять базовую после акции", sales and margin by buyouts, not orders). `AutoPricingService` runs at 09:30 and 19:30 Asia/Tashkent (`AUTO_PRICING_CRON`), reads stock days from the cabinet `GET https://api-seller.uzum.uz/api/seller/shop/{shopId}/product/getProducts` (`avgdsales`, `turnover`, `forecastOutOfStock`) and sends a Telegram report. It changes prices only with `AUTO_PRICING_APPLY=true` in `.env` (default: recommendations only), through `sendPrice` / `sendPromoPrice` with `source = auto`, `PriceChange.rule` and `PriceChange.context` — the rules read that journal back (one change per SKU per day, cooldowns, revert after supply / sales drop). Before applying, every rule-proposed change is reviewed by Claude via `OpenclawClient` (`common/ai-price-review.ts`): the AI may only approve, reject or soften (price between current and proposed) — never add changes; if the AI is unavailable in apply mode, nothing is changed (`AUTO_PRICING_AI=false` disables the review). Manual report: `apps/api/scripts/auto-pricing.ts` (`--telegram`, `--dump-stock`) or Actions → «Автоцены». Promo price plan (recommendations only, nothing is changed): `common/promo-plan.ts` + `apps/api/scripts/promo-plan.ts [--sale N]` / Actions → «План цен в акции» — anchor is the SKU's real average buyout price over 28 days (90 if none), low stock → minimal 1% discount, slow sellers → 7% below anchor, strong flow → +3% (not for лицевые), capped at base −1% and floored at 15% margin; uses the same inputs as `AutoPricingService.collect`.
- Ad agent: `AdAgentService` (`modules/ads`, rules in `common/ad-agent.ts`) runs daily at 10:00 Asia/Tashkent (`AD_AGENT_CRON`) and only sends advice to Telegram (target: reach and traffic for slow sellers, ДРР ≤ `AD_AGENT_MAX_DRR_PERCENT`, default 10). Data via the `UZUM_INTERNAL` Bearer token: `getProducts`, `POST /api/seller/cpo/advertisements/search` («Буст заказов» bids), `GET /api/seller/advertising/management/ad-campaign` («Буст в ТОП»), and Cube.js `https://analytics-seller.uzum.uz/cubejs-api/v1/load` (cubes `SellerReportProductFunnelSku`, `AdvertisingCpoFunnel`, `AdvertisingDailyFunnel`; retry on `Continue wait`). Campaign lists are paged by at most 20 (`size` > 20 → `illegal-argument-001`). Both agents notify via the Telegram toggle `notifyAgents` («Автоцены и реклама»). Manual run: `apps/api/scripts/ad-agent.ts` or Actions → «Реклама»; both agent workflows first print server version, deploy log tail and the API journal lines of the agents.
- Ad bot («Буст в ТОП»): rules in `common/ad-bot.ts`, `AdBotService` (`modules/ads`) runs daily at 11:00 Asia/Tashkent (`AD_BOT_CRON`). **Proposals only by default**; it changes the cabinet only with `AD_BOT_APPLY=true` in `.env`. Reads active campaigns, keywords via `GET …/ad-campaign/{id}/advertisement?page&size` (size ≤ 10), per-keyword stats from Cube `AdvertisingDailyFunnel` by `bid_id` (= advertisement id), real buyer queries from `AdvertisingFeedDailyFunnel.search_query`, colour stock via `GET /seller/product/skugroup/sku?skuGroupIds=a,b` + `getProducts`. Rules: bids by ДРР/no sales/low reach — the ДРР target is per colour group (`groupDrrTarget`, rule A12): `AD_AGENT_MAX_DRR_PERCENT` for normal stock, but a slow colour (≥ 60 days of stock by the cabinet forecast) may run up to its margin − 5 п.п., capped at 30%, because there the ad's job is to turn the stock over; new keywords from selling buyer queries (Latin-script = Uzbek queries are added with ≥ 1 click even without a sale, at 15 000 — the campaigns have no Uzbek phrases, so "needs a sale" would never find them), stop words (минус-слова) from words of non-selling queries (≥ 300 impressions or ≥ 10 clicks in 28 days, no sales or add-to-cart, not present in any selling query or in the phrase; Uzum allows ≤ 58 per keyword; billing is per impression). Writes with `PUT /seller/advertising/management/ad-campaign/{id}` `{ advertisements: [{ action: NEW|EDIT|SUSPEND, advertisement: { id?, cpm, promotionType: 'QUERY', query, skuGroupId, stopWords } }], budgetConfig, name, period }` → 204, only changed ads; budget/name/period are sent unchanged. Guards: bid 9 500…`AD_BOT_MAX_BID` (50 000), cooldown 3 days per keyword, ≤ `AD_BOT_MAX_CHANGES` (30) per run, low colour stock → bid to minimum. Journal: `AdBotChange`. Manual run: `apps/api/scripts/ad-bot.ts [--apply] [--telegram]` or Actions → «Рекламный бот».
- Auto-bidder («Авто-ставка», modelled on SellerX): per-keyword policies in `AdAutoBidPolicy` (target reach 10…100 %, max bid, max ДРР), keyed by `key` = `campaignId|skuGroupId|normalizeQuery(query)` because Uzum recreates the advertisement with a new id on every bid edit (`adId` is only the last known id; Cube stats are summed over all ids of the key via `AdBotService.keywordStatsByKey`) edited on the web page `/auto-bidder` (`AutoBidderClient.tsx`, API `ads/auto-bidder/*` in `modules/ads/ads.controller.ts`). Rules in `common/auto-bidder.ts`: the bid buys *reach*, not position — with the cabinet's bid ladder (position → CPM → % impressions) the policy picks the cheapest step that buys the target reach; without it the bot only keeps the bid within the cap and ДРР and raises by 10 % when impressions are low. ДРР guard kicks in after enough data (spend ≥ 30 000 or ≥ 20 clicks / 14 d): ДРР > max → cap lowered 15 % for the run; ДРР > 2×max for both 7 and 14 d (or spend with no sales) → policy paused (`pausedAt`), bid to minimum, re-enable by hand. Step ≤ 25 % per run, rounding 500, cooldown 2 h. `AutoBidderService` runs hourly (`AUTO_BIDDER_CRON`), proposals only unless `AUTO_BIDDER_APPLY=true`; writes through `AdBotService.apply` (same PUT), journal `AdBotChange` with reason prefixed «авто-ставка». `AdBotService` skips bids of managed keywords (`AdBotInput.managed`) but still adds stop words to them. The ladder endpoint is **not known yet**: `AD_BID_LADDER_URL` is a GET template with `{campaignId}` `{adId}` `{skuGroupId}` `{query}` placeholders parsed by `parseLadder`; capture it from the cabinet's Network tab when editing a «Буст в ТОП» bid. Manual run: `apps/api/scripts/auto-bidder.ts [--apply] [--telegram]` or Actions → «Авто-ставка».
- Slot auto-booking (FBS, modelled on SellerX «Автобронь»): `SupplySlotWatch` has `desiredFrom`/`desiredTo` (Tashkent days, inclusive) and `autoBook`; pure selection in `common/slot-booking.ts` (`pickSlot` = earliest future slot inside the window, capacity 0 skipped). `SuppliesService.watchSlots` (every 5 min) notifies only about a matching slot; with `autoBook` **and** `SUPPLY_AUTO_BOOK_APPLY=true` it books through `reserveSlot`, whose request is an `.env` template (`SUPPLY_BOOK_SLOT_REQUEST` = `METHOD /path`, `SUPPLY_BOOK_SLOT_BODY` = JSON; placeholders `{invoiceId}` `{slotId}` `{dropOffPointId}` `"{orderIds}"` `{from}` `{to}`) because the OpenAPI swagger is RBAC-blocked and the booking endpoint is **not confirmed yet** — discover it with Actions → «Документация Uzum API» (`--probe`: GET/OPTIONS over candidate FBS paths, read-only) or from the cabinet Network tab. Result → `bookedAt/bookedSlotFrom/bookedSlotTo`, `Supply.slotFrom/slotTo`, `NotificationLog` SLOT_BOOKED, Telegram via `notifySlotFound`.
- Cabinet session (`UZUM_INTERNAL` token): instead of pasting a Bearer token by hand, the owner can save a separate cabinet **employee** login/password (Settings → Отзывы Uzum → «Вход под сотрудником», stored encrypted as `UZUM_CABINET_LOGIN`). `CabinetAuthService` (`modules/integrations`, pure logic in `common/cabinet-auth.ts`) runs every 20 min (`CABINET_AUTH_CRON`), refreshes via `POST https://api-seller.uzum.uz/api/oauth/token` (`grant_type=refresh_token`, falls back to `grant_type=password`; Basic auth with the cabinet's public client key `b2b-front`) and writes the fresh access token into `UZUM_INTERNAL`, so reviews, promos and ads keep working. On failure it marks the integration ERROR and notifies Telegram at most every 3 h. Never navigate the owner's browser in the cabinet by guessed URLs or the logo — it logs the owner out.
- Docker runtime applies the schema with `prisma db push` (not migrations) and runs `prisma/seed.cjs` on every start; ports `3000` (web) and `4000` (api) are bound to `127.0.0.1` and expected to sit behind a reverse proxy (`docker-compose.traefik.example.yml`).
- Prefer a short project path without OneDrive on Windows; Docker base image is pinned to Node 20 to dodge an `npm ci` hang seen on Docker Desktop/Windows.
- Money-affecting changes must be verified on the server with a live smoke test and a manual reconciliation of 10–20 rows against the real Uzum cabinet (`SERVER_CHECKLIST.md`, `PROJECT_STATUS.md`).
