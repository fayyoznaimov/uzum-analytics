# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Uzum Analytics — a self-hosted seller analytics cabinet for the Uzum marketplace: sales, profit, cost price, warehouse, supplies, goals, Telegram notifications, and a "wallet" that forecasts when money lands in the Uzum withdrawal basket. npm-workspaces monorepo: `apps/api` (NestJS 11) + `apps/web` (Next.js 15 App Router, React 19), Postgres via Prisma, deployed with Docker Compose. Product, UI, docs, commits, and all user-facing strings are in **Russian** — keep new strings Russian.

## Architecture

### API (`apps/api`)
- **No per-feature Nest modules.** A single `AppModule` (`src/app.module.ts`) registers every controller and provider flat. A feature = a folder `src/modules/<feature>/` with `<feature>.controller.ts` + `<feature>.service.ts`. When adding a feature, wire both arrays in `app.module.ts`.
- **Business logic is extracted into pure functions in `src/common/`** (`finance.ts`, `payout-basket.ts`, `payout-forecast.ts`, `order-state.ts`, `advertising.ts`, `inventory-report.ts`, `inventory-analytics.ts`, `sku-payout.ts`, `profit-days.ts`, `financial-statement.ts`, `fbo-supply-summary.ts`, `period.ts`, `pricing.ts`, `promo-pricing.ts`, `auto-pricing.ts`, `ai-price-review.ts`, `ad-agent.ts`, `ad-bot.ts`, `promo-plan.ts`). Services orchestrate Prisma + these functions; put testable logic here, not in services.
- Shared providers: `PrismaService`, `CryptoService`, `TelegramClient`.
- `main.ts`: global prefix `/api`, `helmet`, CORS restricted to `WEB_ORIGIN` (comma-separated), global `ValidationPipe` (`whitelist` + `forbidNonWhitelisted` + `transform`), env validation at boot (`DATABASE_URL`, `JWT_SECRET` ≥ 32 chars, `APP_ENCRYPTION_KEY`).
- **Auth**: JWT bearer, 12h expiry. `AuthGuard` is applied **per controller/route** with `@UseGuards(AuthGuard)`, not globally — new endpoints are public unless guarded. `ThrottlerGuard` is the one global guard. A single admin user is seeded from `ADMIN_EMAIL`/`ADMIN_PASSWORD`.
- **Integration credentials** (`UZUM`, `UZUM_INTERNAL`, `UZUM_CABINET_LOGIN`, `OPENAI`, `TELEGRAM`) are stored in the DB (`IntegrationCredential`), **encrypted at rest** with AES-256-GCM by `CryptoService` using `APP_ENCRYPTION_KEY` (base64, decodes to exactly 32 bytes). They are configured through the Settings UI at runtime, not via env.
- **Sync** (`SyncService`): `@Cron` jobs (schedules from env: `SYNC_CRON`, `ORDER_NOTIFY_CRON`, `SUPPLY_SYNC_CRON`, `SLOT_WATCH_CRON`, `AD_RATE_DIGEST_CRON`, …) pull from the Uzum Seller OpenAPI base `https://api-seller.uzum.uz/api/seller-openapi` (`/v1/shops`, `/v1/product/shop/:id`, `/v1/finance/orders`, `/v1/finance/expenses`). Manual run: `POST /api/sync/run`; poll `GET /api/sync/runs`. Sync is defensive: unrecognized payload shapes throw rather than wiping stored data; pagination has hard page caps. 403/404 on `/v1/shops` and the finance paths are retried as flaps (24–26.10.2026 `/v1/shops` answered «404 Seller with id 351945 not found» three times, the next run passed). Failure alerts of frequent jobs (full sync, ladder, auto-bidder) follow `common/failure-alert.ts`: Telegram only from the 2nd consecutive failed run, reminders at most every 6 h, one «✅ снова работает» after a notified streak; a streak counts as notified only after the message was actually sent (`markNotified`), so a lost message is retried on the next failure (state in memory — an API restart resets it).

- **Зависшие заказы и возвраты** (`ReturnsWatchService`, `common/returns-watch.ts`): `RETURNS_WATCH_CRON` (по умолчанию `35 * * * *`, порог `STUCK_ORDER_WATCH_DAYS`=14, выключается `RETURNS_WATCH_ENABLED=false`). Uzum не отдаёт ни ожидаемую дату возврата, ни событие «склад принял товар»: статус заказа меняется задним числом, а товар возвращается отдельно и позже. Поэтому сверяются два источника — переходы `OrderStatusHistory` из состояния `WAITING` и снимки складских количеств SKU из кабинета (`quantityAvailable` / `quantityReturned` / `quantityDefected` → `SkuWarehouseSnapshot`, пишутся только изменившиеся SKU). Возврат считается доехавшим, только когда вместе с «возвращено» вырос и остаток; рост брака означает, что в продажу штука не вернётся. Каждое событие уходит в Telegram один раз (`dedupeKey` в `NotificationLog`).

### Core domain invariants — do not "improve" these casually
- **Money timeline**: `dateIssued` (actual handover to buyer) → 10 full calendar hold days → next day the amount becomes `basketEligibleAt` (enters the withdrawal basket) → then paid out on the shop's payout schedule. Returns reduce money automatically because the Finance API `order.payout` is already net of returns — basket/profit are computed from that net payout. A return *after* issue additionally writes a negative `OrderFinancialEvent` (`RETURN_REVERSAL`) into an audit-trail journal that nothing reads yet; write errors are logged and surfaced in the sync run message. Reference: `docs/UZUM_WALLET_BASKET.md`, `common/payout-basket.ts`, `common/payout-forecast.ts`.
- **Advertising spend for actuals is never modeled or averaged.** It is rebuilt solely from real Uzum expense-ledger rows — code `У000120` (per-order boost), `У000119` (top/campaign boost). Where the fact isn't published yet, the UI may show an estimate from the last *observed* per-product rate, always explicitly labeled as an estimate. `common/advertising.ts`.
- **All day/hour bucketing is `Asia/Tashkent`.** Use the `Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Tashkent' })` helpers in `common/period.ts` (API) / `web/lib/period.ts` (client). Don't add raw `new Date()` local-time date arithmetic. API list endpoints take `from` / `to` / `days` / `compare` query params resolved by `resolvePeriod`.
- Profit/margin figures are shown only when every input (payout, cost price, ad fact/coverage) is known; otherwise the code deliberately renders "не рассчитана" rather than a guess. Preserve that "known vs. estimated" distinction in any financial output, including Telegram messages.

### Web (`apps/web`)
- Next.js App Router. **Every `app/<route>/page.tsx` is a one-line re-export** of `components/<Name>Client.tsx`. All real UI lives in the `*Client.tsx` client components; keep it that way.
- `lib/api.ts`: `api()` fetch wrapper — JWT from `localStorage['ua_token']`, auto-`logout()` on 401, `NEXT_PUBLIC_API_URL` base (`/api` in prod). `money()` / `compact()` are ru-RU formatters. `syncAndWait()` triggers + polls a sync.
- `lib/period.ts`: `useAnalyticsPeriod()` hook — selected period persisted to `localStorage` and broadcast across components via a custom window event.
- Styling is **hand-written class-based CSS** in `app/globals.css` (+ `costs-ui.css`, `reviews-ui.css`), no Tailwind, no CSS modules. Charts: `recharts`. Icons: `lucide-react`.
- Web components are written in an intentionally dense, single-line style. Match the surrounding file rather than reformatting.
- `next.config.ts` rewrites `/api/:path*` → `API_INTERNAL_URL` (`http://api:4000` in Docker); `output: 'standalone'` unless `NEXT_OUTPUT_STANDALONE=false`.

### Мониторинг конкурентов и расширение (`extensions/uzum-monitor/`)
Публичный каталог uzum.uz с серверных IP закрыт антиботом, поэтому цены/остатки/счётчики заказов чужих карточек и позиции своих товаров в поиске снимает MV3-расширение в браузере владельца. Поток: экран «Конкуренты» выдаёт 6-значный код (`POST /api/competitors/pairing-code`, auth) → расширение меняет его на токен (`POST /api/competitor-watch/pair`) → далее `GET /api/competitor-watch/targets` и `POST /api/competitor-watch/ingest` с заголовком `x-watch-token` каждые ~3 часа. Логика алертов (демпинг ≥3%, пропал/появился товар → Telegram, дедуп сутки) — `common/competitor-watch.ts`; журнал — модели `CompetitorProduct`/`CompetitorSnapshot`/`SearchPositionSnapshot`. «Упущенная выручка» (экран Склад, `GET /api/warehouse/lost-revenue`) — оценка из `common/lost-revenue.ts`: скорость продаж в дни наличия × дни без остатка по `StockSnapshot`; всегда помечается как оценка.

## Workflow
- Development happens in the local clone on the owner's Windows PC or directly on the server in `~/uzum` (commit + push required; the auto-deploy pipeline only rebuilds when origin/main is AHEAD of the server HEAD, so after committing on the server run the build and `systemctl --user restart uzum-api.service uzum-web.service` manually, loading `.env` first: `set -a; . ./.env; set +a; npm run build`). **After each finished task** (not after every file save): run `npm test` and `npm run test:types:api` (plus `npm run test:web` if `apps/web` changed), then commit with a Russian message and `git push` to `main` without asking — the owner wants every finished change in Git right away. A push to `main` deploys to production within seconds, so never push failing checks or half-done work; say so if a check fails instead of pushing.
- Commands that need the production DB or Uzum/Telegram tokens (`apps/api/scripts/*.ts`, sync, price changes) only work on the server; `.env` and the DB are not in Git.

Guards: bid 9 500…`AD_BOT_MAX_BID` (50 000), cooldown 3 days per keyword, ≤ `AD_BOT_MAX_CHANGES` (30) per run, low colour stock → bid to minimum. Journal: `AdBotChange`. - Auto-bidder («Авто-ставка», modelled on SellerX): per-keyword policies in `AdAutoBidPolicy` (target reach 10…100 %, max bid, max ДРР), keyed by `key` = `campaignId|skuGroupId|normalizeQuery(query)` because Uzum recreates the advertisement with a new id on every bid edit (`adId` is only the last known id; Cube stats are summed over all ids of the key via `AdBotService.keywordStatsByKey`) edited on the web page `/auto-bidder` (`AutoBidderClient.tsx`, API `ads/auto-bidder/*` in `modules/ads/ads.controller.ts`). Rules in `common/auto-bidder.ts`: the bid buys *reach*, not position — with the cabinet's bid ladder (position → CPM → % impressions) the policy picks the cheapest step that buys the target reach; without it the bot only keeps the bid within the cap and ДРР and raises by 10 % when impressions are low. ДРР guard kicks in after enough data (spend ≥ 30 000 or ≥ 20 clicks / 14 d): ДРР > max → cap lowered 15 % for the run; ДРР > 2×max for both 7 and 14 d (or spend with no sales) → policy paused (`pausedAt`), bid to minimum, re-enable by hand. Step ≤ 25 % per run, rounding 500, cooldown 2 h. `AutoBidderService` runs hourly (`AUTO_BIDDER_CRON`), proposals only unless `AUTO_BIDDER_APPLY=true`; writes through `AdBotService.apply` (same PUT), journal `AdBotChange` with reason prefixed «авто-ставка». `AdBotService` skips bids of managed keywords (`AdBotInput.managed`) but still adds stop words to them. Billing is close to the bid, so a bid above the 100 % step buys nothing. Actions «Объявления кампании» with «ladder» prints, per active ad, the position and reach the current bid buys and the price of top-10 and of 100 %.
